# III-Drone-Interfaces

`iii_drone_interfaces` defines the ROS interface contract shared across the III packages. It is the transport layer for messages, services, and actions consumed by control, mission, supervision, simulation, the CLI, and ground control.

## Package Role

This package exists to centralize:

- message schemas for state, targets, maneuvers, references, and perception products
- service schemas for configuration, supervision, charging/gripper control, and mission support
- action schemas consumed by supervision and operator tooling

Keeping the interfaces here prevents package-to-package schema drift and makes transport changes explicit.

## Interface Inventory

### Messages

The message set covers several areas:

- control/state: `State`, `Reference`, `ReferenceTrajectory`, `TrajectoryMode`, `TrajectoryComputeTime`
- awareness/mission: `CombinedDroneAwareness`, `Maneuver`, `ManeuverQueue`,
  `Target`, `MissionModeStatus`, `MissionModeRegistryEntry`,
  `InspectionStartEligibility`, `StringStamped`
- perception: `ProjectionPlane`, `SingleLine`, `Powerline`, `PLMapperCommand`
- payload/charging: `GripperStatus`, `ChargerStatus`, `ChargerOperatingMode`

### Services

The service layer includes:

- configuration services such as `GetParameterYaml`, `GetDeclaredParameters`,
  `LoadParameters`, `SaveParameters`, `SetParameterFromGC`, and the boot-only
  `SetBootParameter`/`GetPendingBootParameters`/`ActivatePendingBootParameters`
  transaction.
- mission/control services such as `ComputeReferenceTrajectory`, `GetReference`, `SetGeneralTargetYaw`, `SetTargetCableId`
- supervision/system services such as `SystemCommand`, `GetManagedNodes`
- payload/perception services such as `GripperCommand`, `PLMapperCommand`, `UpdatePowerlineOverview`

### Actions

Actions are declared here for maneuver execution, mission behavior, supervision,
and operator workflows.

### Maneuver request and reference ownership

Each maneuver action goal carries `request_identity`, generated by the Mission
dispatcher before dispatch. Both behavior-tree maneuver wrappers and the
CustomOperation dispatcher use the same process-wide generator and ownership
handshake. `ManeuverReferenceStream.request_identity` identifies the goal that
owns the published reference. The dispatcher supplies this
internal correlation field; it is not a mission-catalog parameter or an operator
input. Identity generation is independent of ROS time and uses a process-unique
random epoch, so restarting at simulated time zero does not reuse goal ownership.

Request identity and stream identity serve different purposes. A new goal gets
a new request identity. Its reference stream can receive a new `stream_id`
during recovery while retaining the same request identity. Retaining a reference
through a provider handoff also preserves its originating request identity.
Sequence numbers remain local to a stream generation.

The consumer may continue the current goal's reference while an explicitly
prepared successor is pending. It admits the successor only under that pending
request identity. Once the successor takes over, or a request is canceled,
delayed samples from the retired request cannot become a later goal's reference.
Ownership is checked again when consuming a cached reference; cancellation also
revokes samples that arrived before the cancellation.
Empty, malformed, and unrelated identities fail closed before they can replace
the consumer's cached reference or receive an applied acknowledgement. Recovery
retains the faulting request's identity, including a fault on its first sample.

`ClearManeuverQueue.request_identity` optionally limits queued-item removal to
that exact goal. Automatic CustomOperation cleanup always uses this scope; it
sends no clear without an owned goal. A malformed nonempty identity is rejected.
An empty identity retains the explicit operator command to clear the whole
queue. Clearing queued items does not cancel the current maneuver. Mode
activation/deactivation relies on owned action cancellation rather than issuing
an asynchronous global clear that could remove the next mode's goal.

All canonical maneuver producers and consumers must be rebuilt together after
this interface change. An old goal with no request identity is not accepted as
a native mission reference through a compatibility fallback.

## Generation Model

`iii_drone_interfaces` is a pure interface package. It should not contain runtime logic. Its job is to:

- declare interface files
- export the `rosidl_interface_packages` group
- generate code through `rosidl_default_generators`

## Tests

The current test coverage checks:

- every `.msg`, `.srv`, and `.action` file on disk is declared in CMake
- required package metadata and generation dependencies are present
- core interface categories remain available in the manifest

Typical package-only commands:

```bash
colcon build --packages-select iii_drone_interfaces
colcon test --packages-select iii_drone_interfaces --ctest-args --output-on-failure
colcon test-result --verbose
```

## Maintenance Rules

- treat interface changes as cross-package changes
- update downstream adapters/tests when fields are added or renamed
- keep file declarations in sync with `CMakeLists.txt`; the tests enforce this

## Compatibility

`MissionModeStatus.modes` is the typed replacement for parsing the legacy
per-mode `StringStamped` JSON status topics. Those legacy topics remain
published during migration. Because ROS interface hashes change when fields are
added, `iii_drone_interfaces`, mission, runtime, and all consumers must be
rebuilt and deployed together even though the field is additive at the source
level.
